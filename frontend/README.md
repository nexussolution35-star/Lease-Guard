# LeaseGuard frontend

Vite + React 19 + TypeScript (strict), TanStack Router (file-based routes), TanStack Query, Tailwind CSS v4
with shadcn/ui-style components, Zustand, Zod, react-hook-form. Part of the pnpm monorepo; domain types and
business rules come from `@leaseguard/domain`, the typed API client from `@leaseguard/api-client`.

LeaseGuard is monitoring and communication only: the frontend never collects or processes payments.

## Structure

```
  app/
    App.tsx                Providers + router

    router/                router.ts (createAppRouter, router context), AppRouter.tsx (live auth context),
                           routes/ (file routes; routeTree.gen.ts is generated by `tsr`)
    layouts/               RootLayout (shell, /login renders bare), default pending/error/not-found screens
  features/<feature>/
    api/                   Data-source seam: source.ts (interface + list params), apiSource.ts (the API
                           implementation), selectSource.ts (lazy source), queries.ts (TanStack Query
                           hooks and keys)
    components/            Feature screens (features/properties/components/PropertyListScreen.tsx is the
                           reference list screen)
  features/auth/           Supabase session provider, login form/screen, route guard, safe redirects,
                           password links (forgot password, change password by email link, set a new
                           password on /auth/reset-password)
  features/account/        `GET`/`PATCH /me`, workspace resolution, remembered workspace, workspace gate,
                           edit-profile and change-password (send link) dialogs
  features/notifications/  Notification source and hooks (list, unread count, mark read)
  features/reports/        Report definitions (static metadata)
  components/
    ui/                    shadcn/ui primitives
    shared/                DataTable, states (Loading/Error/Empty/NoActiveWorkspace), RecordQueryView, …
    forms/                 react-hook-form field components and `zodResolver`
    layout/                Application shell (sidebar, topbar, breadcrumbs, account menu, workspace switcher)
  lib/data/                Generic data-layer helpers: ListParams/Page, query keys, lazySource,
                           useCompanyQuery, useActiveCompanyId
  services/
    api/                   config.ts (env validation), supabase.ts (auth client), client.ts (the single
                           API client), queryClient.ts
    query.ts               List-query state types for table components
  store/                   Zustand store: the active workspace only (in memory; no records)
  test/                    Test helpers and small fixtures (fake API, sample records); never used by the app
```

## Data

There is no demo or offline mode, and the app holds no business data of its own: it signs in with
Supabase Auth (email/password) and reads every record from the LeaseGuard API through
`@leaseguard/api-client`. Every route except `/login` requires a session.

The API covers properties, units, tenants, leases, statements, monitoring events, payment arrangements
(monitoring records only), communications and notifications. Each `apiSource.ts` maps its list params
to the endpoint's real query parameters only (sort fields are the generated `*SortField` types; the API
rejects unknown values with 400), sends the company from the query key as `X-Company-Id`, answers
`get` with null for a 404 or a non-UUID id (without a request), and rethrows every other `ApiError`. The
generated response DTOs are assignable to the `@leaseguard/domain` types without casts.

Screens use the hooks in `features/<feature>/api` (for example `usePropertyList`, `usePropertyQuery`).
Query keys start with the entity and the active company id, so switching workspace never shows another
company's cache. Global search and navigation badge counts are not offered: the API has no endpoints for
them yet.

### Signed-in user and workspace

After Supabase sign-in, `WorkspaceGate` (in `RootLayout`, around the shell) loads `GET /api/v1/me`
with TanStack Query (key `['me', userId]`) before any company data is requested:

1. The workspace is resolved by `resolveWorkspace` (`features/account/workspace.ts`): the company already
   selected in this tab, else the one remembered on this browser (`localStorage`
   `leaseguard.api.workspace.<userId>`, a convenience only), as long as the user is still a member there;
   otherwise the default membership, or the first one. The gate calls `setActiveCompany` and remembers
   the choice.
2. No memberships: a "No workspace access" screen with sign-out. A signed-in user without a LeaseGuard
   profile (`/me` answers 404) sees the same screen.
3. `/me` fails: an error state with "Try again" (and sign-out). A 401 signs the user out, which returns
   them to `/login`.

The sidebar's workspace switcher lists the memberships with the user's role in each; switching sets the
active company, and because every company-scoped query key carries the company id, screens refetch for
the new company. Signing out clears the query cache and the active company.

### Account menu (top bar)

Shows the user's full name, email and role in the active company, and offers:

- **Edit profile**: full name, job title, phone and WhatsApp number (stored as E.164; South African local
  formats are accepted), validated with zod and saved with `PATCH /api/v1/me`; an emptied optional field is
  sent as null and cleared. The `me` query is updated and invalidated afterwards.
- **Change password**: by email link, never by typing the current password. Supabase Auth runs with
  secure password change on (`secure_password_change = true` in `supabase/config.toml`; switch on
  Authentication → Email → Secure password change on the hosted project), so `updateUser({ password })` is
  only accepted from a recently authenticated session. The dialog calls
  `resetPasswordForEmail(<signed-in email>, { redirectTo: <origin>/auth/reset-password })` and shows "We
  sent a link to …", with a 60-second resend cooldown (or the wait Supabase reports on a 429). The link
  opens `/auth/reset-password` (the same page as "Forgot password"), where the new password is set (8–72
  characters, confirmed) and the user continues into the app signed in. An expired link sends a signed-in
  user back to the account menu for a new one.
- **Switch workspace** (only with more than one membership), **Theme**, **Sign out**.

The notification centre reads `GET /api/v1/notifications` for the active workspace (an unread-only page of
one for the badge, refreshed every minute; the newest 20 when the panel opens) and marks one or all read
with `POST /api/v1/notifications/{id}/read` and `POST /api/v1/notifications/read-all`.

## Environment

Vite reads the single repository-root `.env` (`envDir` is the repository root; see `../.env.example`). Only
`VITE_*` variables reach the browser; never put secrets in them.

| Variable | Required | Purpose |
| --- | --- | --- |
| `VITE_API_URL` | yes | Backend origin, e.g. `http://127.0.0.1:3000` |
| `VITE_SUPABASE_URL` | yes | Supabase URL, e.g. `http://127.0.0.1:54321` |
| `VITE_SUPABASE_ANON_KEY` | yes | Public anon key (RLS applies) |

An invalid configuration renders a startup error screen listing the problems; nothing else loads. A
`VITE_*` variable holding a Supabase secret or service-role key stops both the build and startup. Other
`VITE_*` variables (for example a leftover `VITE_DATA_SOURCE`) are ignored. Unit tests use fixed,
unreachable endpoints (`test.env` in `vite.config.ts`) and fake the API client; they never read `.env`.

## Commands

Run from `frontend/`:

- `pnpm dev`: Vite dev server
- `pnpm build`: generate routes, type-check, production build
- `pnpm typecheck`: generate routes and type-check
- `pnpm test`: Vitest (jsdom)
- `pnpm lint`: oxlint
- `pnpm routes:generate`: regenerate `src/app/router/routeTree.gen.ts`
