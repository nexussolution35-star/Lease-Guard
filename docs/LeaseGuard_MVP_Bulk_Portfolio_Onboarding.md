# LeaseGuard MVP Enhancement: Portfolio Onboarding and Tenant Enrolment

**Document type:** MVP feature enhancement  
**Product:** LeaseGuard  
**Area:** Client onboarding, lease loading and statement processing  
**Status:** Proposed enhancement to the existing LeaseGuard specification  
**Relationship to existing specification:** This document extends the current onboarding workflow. It does not replace LeaseGuard's existing product behaviour, operating model or accounting-system approach.

---

## 1. Purpose

Improve the way a property manager initially loads a property and its tenants into LeaseGuard.

The existing LeaseGuard workflow already establishes that:
- Lease terms are loaded once when a client is onboarded.
- The client uploads PDF statements generated by its existing accounting system.
- LeaseGuard reads those statements and compares them against the lease terms.
- Each client's statement layout is configured, with uncertain extraction results sent to a person for review.
- The client can start with one property and provide three statements from any three tenants before expanding.
- No accounting-system API integration is required for the initial workflow.

This enhancement defines a practical way to carry out that onboarding at scale. Rather than requiring a manager to create every tenant and lease manually, LeaseGuard should allow documents to be uploaded in batches, extract the available information, propose matches and ask the manager to resolve exceptions.

**The improvement is to the onboarding and data-loading experience, not a change to what LeaseGuard does.**

## 2. Existing workflow and proposed improvement

| Existing LeaseGuard behaviour | Enhancement proposed in this module |
|---|---|
| Lease terms are loaded once during onboarding. | Allow multiple lease PDFs to be uploaded together and processed as one onboarding batch. |
| Statements are uploaded as PDFs from the existing accounting system. | Allow multiple statement PDFs to be uploaded together, while retaining the existing monthly statement-upload workflow. |
| A reader is configured for each client's statement layout. | Keep the client-specific reader and show file-level processing results during a batch upload. |
| The reader extracts tenant, unit, charges, payments and balance. | Add structured extraction of available lease terms and matching between lease, tenant and statement records. |
| Uncertain information goes to a person instead of being guessed. | Provide a review queue for uncertain fields, unmatched documents and conflicting information. |
| The first onboarding can start with one property and three statements from any three tenants. | Preserve this pilot approach, then allow the client to load the rest of the property's lease pack and expand to more properties. |
| Findings are reviewed before tenant messaging is enabled. | Keep messaging disabled until the client has reviewed the findings and explicitly approved activation. |

## 3. MVP objective

A property manager should be able to onboard a property by providing its existing lease documents and sample statements, without manually creating each tenant record where the documents already contain the required information.

The MVP must support two stages:

### Stage A: Initial pilot
1. The client selects one property to onboard.
2. The client uploads the lease documents for that property, or the agreed initial lease sample if the portfolio is being tested in stages.
3. The client uploads three statements from any three tenants, as described in the existing LeaseGuard onboarding proposal.
4. LeaseGuard processes the documents using the client's configured statement reader.
5. The manager reviews extracted information, proposed matches and exceptions.
6. LeaseGuard shows the findings before any tenant messaging is enabled.

### Stage B: Complete property onboarding
After the pilot has been checked and accepted:
1. The manager uploads the remaining lease PDFs for the property in a batch.
2. The manager uploads the relevant current tenant statements in a batch, or continues with the normal monthly statement process.
3. LeaseGuard extracts and matches the information against the records already loaded.
4. The manager reviews only unmatched, incomplete, uncertain or conflicting records.
5. The manager approves the records for monitoring.

This allows LeaseGuard to start small as originally proposed while still providing a scalable route to onboarding an entire property.

## 4. User workflow

### Step 1: Select the property
The manager selects an existing property or creates one using the current LeaseGuard property setup.

Capture only the property information needed to identify it, such as:
- Property name
- Property address
- Client / owning organisation
- Existing property reference, if available

### Step 2: Upload existing documents

Provide separate upload areas for:

**Lease agreements**
- Support multiple PDF lease agreements in one upload batch.
- Retain the original filename and source document.
- Prefer one lease per PDF, but do not assume that every uploaded file contains only one lease.
- Identify likely duplicate files and warn the user.

**Tenant statements**
- Support multiple PDF statements in one upload batch.
- Continue to accept statements generated by the client's existing accounting system.
- Retain the existing client-specific statement-layout configuration.
- Support the initial three-statement pilot described in the existing proposal.

**Optional tenant register**
- Allow a CSV or XLSX tenant register as supplementary information, if the client already has one.
- Use it to assist with tenant, account, unit and contact matching.
- Do not make this file a mandatory onboarding requirement.
- Do not treat it as a replacement for the lease agreement or accounting statement.

The manager should not have to enter every tenant manually just to begin processing the uploaded documents.

### Step 3: Extract information

Use the existing document-reading approach and extend it to lease onboarding.

**From lease agreements, extract available information such as:**
- Tenant legal or trading name
- Property and unit / shop number
- Lease commencement date
- Lease expiry date
- Rental amount
- Escalation percentage, frequency and effective date
- Renewal option and notice period
- Deposit amount
- Bank guarantee amount and expiry date
- Tenant contact details, where present

**From tenant statements, retain the existing extraction requirements:**
- Tenant
- Unit
- Charges
- Payments
- Balance

Where available, also identify:
- Tenant/account reference
- Statement date or period
- Opening balance
- Closing balance

The statement reader must continue to validate that extracted figures add up. If it is unsure, it must send the item for human review rather than guessing.

### Step 4: Match the documents

LeaseGuard should attempt to associate each lease and statement with the correct tenant and unit.

Use the strongest available identifiers first:
1. Exact tenant or account reference.
2. Exact property and unit reference.
3. Tenant name together with property or unit.
4. Similarity-based match as a suggestion requiring confirmation.

Do not automatically merge records just because tenant names look similar.

Each document should receive a clear result:
- **Matched:** A reliable match has been found.
- **Suggested match:** A possible match needs manager confirmation.
- **Unmatched:** No reliable matching record has been found.
- **Conflict:** Important identifiers or values disagree.
- **Duplicate:** The file appears to have been uploaded already.
- **Needs review:** Extraction is incomplete or uncertain.

A lease may be loaded before its first statement is available. An unmatched statement must be retained for later review rather than discarded.

### Step 5: Review exceptions

Provide one review area where the manager can see:
- Original document name and type.
- Extracted tenant and unit details.
- Proposed tenant/lease match.
- Missing information.
- Conflicting information.
- Uncertain extracted fields.
- A way to open or inspect the source document.

The manager can:
- Confirm or reject a proposed match.
- Correct an extracted value.
- Link a document to an existing tenant or lease.
- Create a draft tenant record when no match exists.
- Mark a document as a duplicate.
- Retry a failed document.
- Leave an item unresolved and return to it later.

Manual changes must be recorded with the user, timestamp, previous value and new value.

### Step 6: Preview and approve

Before records are made available to the monitoring process, show an import summary:
- Lease documents uploaded, processed and failed.
- Statement documents uploaded, processed and failed.
- Tenant and lease records identified.
- Statements successfully matched.
- Suggested, unmatched, duplicate and conflicting records.
- Missing or unverified contact details.

The manager must be able to return to the review area before approving.

### Step 7: Make approved records available to LeaseGuard

After authorised approval:
- Save approved tenant, property, unit and lease information in LeaseGuard's existing data model.
- Associate statements with the correct tenant/account.
- Preserve links to source documents.
- Make approved lease information available to the existing lease-monitoring rules.
- Keep unresolved records clearly marked and out of automated checks until they are resolved, unless a defined partial-activation rule is approved.

**Approval of document import must not automatically activate tenant messaging.** The existing rule remains: the client reviews the findings and approves messaging before any tenant communication is sent.

## 5. Monthly statement workflow remains unchanged

This enhancement is primarily about initial onboarding. It must not introduce a new monthly administrative burden.

After onboarding:
1. The bookkeeper or property manager uploads the month's PDF statements generated by their existing accounting system.
2. LeaseGuard reads each statement using the configured client-specific reader.
3. The statement is matched to the existing tenant and lease records.
4. LeaseGuard compares billed amounts with the lease terms and checks the statement balances.
5. Uncertain readings or unmatched statements go to a person for review.
6. The existing monitoring rules identify relevant events and actions.

The client continues using its existing accounting system. LeaseGuard does not issue invoices, maintain the client's accounting ledger, collect rent or move money.

## 6. Required MVP screens

### A. Property onboarding
- Select or create property.
- Show onboarding stage and status.
- Explain the initial pilot process.

### B. Document upload
- Separate lease and statement upload areas.
- Multiple PDF upload support.
- Optional CSV/XLSX tenant register.
- Per-file upload status and validation feedback.
- Duplicate-file warning.

### C. Processing results
- Per-file extraction status.
- Processing errors and retry action.
- Clear distinction between uploaded, processed and approved.

### D. Matching and review
- Matched, suggested, unmatched, conflict, duplicate and needs-review filters.
- Extracted values and source document access.
- Confirm/reject match and correct-value actions.
- Audit history for manual changes.

### E. Import summary and approval
- Counts of tenants, leases and statements.
- Outstanding exceptions.
- Approval action for authorised users.
- Clear notice that tenant messaging is still disabled.

These screens should fit into the existing LeaseGuard manager experience. They are not a separate product or a replacement dashboard.

## 7. Data and system considerations

Reuse LeaseGuard's existing entities for:
- Organisations / clients
- Properties
- Units
- Tenants
- Leases
- Statements
- Lease events
- Payment arrangements
- Message history

Add onboarding-specific records only where needed to track:
- Upload batch
- Original document and storage reference
- Extraction result and status
- Proposed match and match decision
- Review status
- Import approval
- Audit history

Avoid creating a second tenant or lease data model just for onboarding.

Every extracted value should remain traceable to its source document where practical. Keep original files and extraction results so that a manager can inspect how a value was obtained.

## 8. Validation and safety requirements

- Never invent missing lease terms, tenant details or statement values.
- Do not silently merge tenants based only on similar names.
- Validate dates, rental amounts, escalation percentages and statement arithmetic.
- Preserve original documents.
- Flag uncertain or conflicting data for human review.
- Prevent duplicate uploads from creating duplicate tenant, lease or statement records.
- Enforce organisation and property-level access permissions.
- Protect uploaded leases and statements as confidential client documents.
- Keep bank details on the attached statement, not in WhatsApp message text.
- Do not send tenant messages as a side effect of uploading, extracting, matching or approving documents.

## 9. MVP acceptance criteria

The enhancement is ready for pilot when:

1. A manager can select or create one property for onboarding.
2. A manager can upload multiple lease PDFs in one batch.
3. A manager can upload the three sample statements required by the existing pilot process.
4. A manager can upload multiple statements in a batch when proceeding to full property onboarding.
5. A CSV/XLSX tenant register can optionally assist with matching.
6. Each document has a visible upload and processing status.
7. Lease information and the existing statement fields can be extracted where present.
8. Statement figures are validated and uncertain readings are sent for human review.
9. Lease and statement documents can be matched using available tenant, account and unit identifiers.
10. Ambiguous matches are not silently confirmed.
11. A manager can correct extracted values and resolve matching exceptions.
12. The manager can preview the proposed records before approval.
13. Approved records are saved into LeaseGuard's existing data model without creating duplicates.
14. Approved lease information can be used by the existing monitoring rules.
15. The initial pilot can show findings before tenant messaging is enabled.
16. The normal monthly statement-upload process remains available after onboarding.
17. Manual changes and approval actions are auditable.

## 10. Out of scope for this enhancement

The following remain outside the MVP unless separately approved:
- Direct API integrations with MRI, MDA, PropSys, Sage or other accounting systems.
- Replacing or synchronising the client's accounting ledger.
- Automatic invoice generation or VAT calculation.
- Payment collection or handling funds.
- Fully automatic approval of lease terms or ambiguous matches.
- Automatic WhatsApp enrolment or messaging activation.
- Guaranteeing extraction from every scanned, handwritten or poor-quality document.
- Replacing the existing manager approval of findings before tenant messaging.
- A new accounting or property-management platform.

## 11. Suggested implementation order

1. Add batch upload for lease PDFs and statement PDFs.
2. Extend onboarding to extract the required lease terms.
3. Keep and configure the existing client-specific statement reader.
4. Implement tenant, unit, lease and statement matching.
5. Build the exception review and correction workflow.
6. Add import preview, approval and audit history.
7. Connect approved records to the existing monitoring rules.
8. Pilot with one property and three tenant statements before expanding to the full property.

## 12. Product principle

**Keep the existing LeaseGuard workflow. Make the initial loading of its data easier.**

The client continues to use its existing accounting system and upload its statements. LeaseGuard continues to compare those statements against lease terms, identify issues, and surface actions to the right people.

The improvement is that the property manager can provide existing lease and tenant documents in batches, allowing LeaseGuard to do the repetitive extraction and matching work while the manager checks exceptions and approves the result.
